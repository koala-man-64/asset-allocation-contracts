# Deployment Setup

## Recommendation

Do not deploy this repo into `AssetAllocationRG`.

This repo should publish versioned contract artifacts only:

- a Python package from `python/`
- a TypeScript package from `ts/`
- JSON schemas from `schemas/`

The runtime repos should pin a contracts version and deploy against that version. The Azure Pipelines release manifest carries the exact published version for downstream automation.

## Current State

- `azure-pipelines/` owns CI, security, and release for this repo
- CI and security run on the self-hosted `local-docker-agents` pool with the baked contracts toolchain
- release stays on Microsoft-hosted `ubuntu-latest` until the local pool has proven uptime, patching, monitoring, and repeatability
- `.env.web` for release and retained legacy dispatch configuration is generated by `scripts/setup-env.ps1` and applied by `scripts/sync-all-to-azure-devops.ps1`
- this repo has no Azure runtime deployment target and no Azure provisioner scripts
- `azure-pipelines/` is retained as a legacy surface from the previous operating model; do not use it as the canonical deployment path

## What To Provision

Provision package distribution, not Azure runtime infrastructure:

1. Pick a Python package registry.
2. Publish the TypeScript package to the Azure Artifacts npm feed from Azure Pipelines.
3. Publish the Python package to the Azure Artifacts PyPI feed from Azure Pipelines.
4. Configure the `prod-package-release` Azure Pipelines environment approval gate.

## Deploy

This repo has no Azure deployment target.

The operational path is:

1. run `azure-pipelines/ci.yml`
2. run `azure-pipelines/security.yml`
3. publish with `azure-pipelines/release.yml`

`azure-pipelines/release.yml` emits `artifacts/release-manifest.json` in the `contracts-release` pipeline artifact.

## Operate

- Keep the committed Python and TypeScript package versions aligned and treat them as the only release version source of truth.
- Keep `schemas/` regenerated from source by running `python python/scripts/export_schemas.py`.
- Use `scripts/compatibility_gate.ps1` as the cross-repo smoke check before publishing a breaking contract change.

## Release Steps

1. Run `powershell -ExecutionPolicy Bypass -File scripts\setup-env.ps1 -DispatchAppPrivateKeyPath C:\path\to\dispatch-app.pem`.
2. Run `powershell -ExecutionPolicy Bypass -File scripts\sync-all-to-azure-devops.ps1`.
3. Run the contract validation steps:
   - `python -m pytest tests/python/test_contract_models.py tests/test_env_contract.py -q`
   - `cd ts && corepack pnpm typecheck`
   - `powershell -ExecutionPolicy Bypass -File scripts/compatibility_gate.ps1`
4. Publish with `azure-pipelines/release.yml` against `main` after CI and security pass.
   The pipeline reads the committed stable semver from `python/pyproject.toml` and `ts/package.json`, verifies manifest parity, rebuilds both packages, publishes TypeScript and Python artifacts to Azure Artifacts, and retains `release-manifest.json`.
5. Downstream jobs and UI automation should consume the exact package version recorded in the retained release manifest.

## Rollback

- Re-publish or re-tag the previous known-good contracts version.
- Re-run the downstream compatibility workflows against that version.
- Revert any consumer repo updates that pinned the bad version.

## Troubleshoot

- If `ci.yml` fails on schema drift, regenerate `schemas/` from `python/scripts/export_schemas.py` and commit the result.
- If `release.yml` fails before build, inspect the committed manifest versions and confirm both manifests contain the same stable semver.
- If a manual `release.yml` run fails because a version already exists, bump both manifests with `scripts/prepare-release.ps1`, commit the change, and rerun release.
- If TypeScript publish fails, verify `npmAuthenticate@0`, `ts/.npmrc`, and the Azure Artifacts npm registry URL.
- If Python publish fails, verify `TwineAuthenticate@1` and the `AdaptiveAssetAllocation/asset-allocation-packages` feed.

## Dependencies

- Azure Artifacts project feed `asset-allocation-packages`
- Azure Pipelines environment `prod-package-release`
- Local Docker Azure DevOps agents in pool `local-docker-agents` for CI/security
- Downstream repos: `asset-allocation-jobs` and `asset-allocation-ui`

## Notes

- This repo owns package publish configuration only. It does not own Azure runtime provisioning.
- TypeScript and Python publishing target Azure Artifacts for the committed stable semver release version.
- Long-lived public npm publish secrets are no longer part of the repo env contract.
- `scripts/setup-env.ps1` still reads `DISPATCH_APP_PRIVATE_KEY` for the retained legacy GitHub workflow surface and stores newline-escaped contents in `.env.web`.
- Legacy `0.1.x` and `YYYY.M.D-dev.*` contracts versions remain in registries for rollback history but are unsupported for new releases or consumer adoption.
